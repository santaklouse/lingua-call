## 1. Требования и ограничения

**Функциональные (из задания):**

1. Экран выбора родного языка.
2. Экран «создать чат» (получить токен и поделиться) / «подключиться по токену».
3. Экран выбора и проверки камеры/микрофона.
4. Субтитры включаются автоматически и настраиваются.
5. Транспорт — желательно `go-p2p-netcat`.
6. Никаких сторонних платных сервисов.

**Нефункциональные:** работа на реальных устройствах, задержка субтитров
≤ 2 с, приватность речи, устойчивость к разрывам, понятные ошибки NAT.

**Две главные развилки, которые и образуют варианты:**

1. **Как доставляется медиа** (аудио/видео):
   - **(M1) нативный WebRTC media** — отдельное `RTCPeerConnection` с
     `addTrack()`; SDP/ICE гоняются по control-каналу `go-p2p-netcat`;
   - **(M2) media-over-data-channel** — кодировать видео/аудио (WebCodecs) и
     передавать кадрами по тому же потоку.
2. **Где исполняются ASR/MT** (распознавание/перевод): в браузере (WASM),
   в десктоп-приложении (нативные модели), на своём сервере (`lingua-node`).

## 2. Проверенные факты о `go-p2p-netcat` (по коду, 2026-11-07)

| Возможность | Статус | Комментарий |
|---|---|---|
| Байтовый поток по PeerId (`/p2p-netcat/1.0.0/<port>`) | ✅ | TCP, QUIC, WS/WSS, WebTransport, WebRTC Direct, Circuit Relay v2 |
| Native WebRTC **data channel** с аутентификацией PeerId | ✅ | `packages/core/src/native-webrtc.js`; канал `p2p-netcat-v2`, **ordered + reliable** |
| **Аудио/видео как медиа-треки (addTrack/ontrack)** | ❌ | В коде нет ни `addTrack`, ни `ontrack`, ни RTP; SDP создаётся без `m=audio/video` |
| Браузер как **listener** native WebRTC | ⚠️ есть API, не используется | `startNativeWebRtcListener()` browser-safe; нужны стабильная identity и `createAuthResponse`; работает только на главном потоке (вкладка открыта) |
| Pairing-токен `pnc1_` создаётся в браузере | ✅ | `createPairingToken({peerId, service, secret, expiresAt})`; токен = PeerId + порт + 32-байтный секрет (+relayHints/expiry) |
| Приватный rendezvous из токена | ✅ | `deriveRendezvousId`, шифрованный signaling; аудио/байты через трекеры не идут |
| Signaling | ✅ | Публичные Nostr-релеи (kind 25050) + WebTorrent-трекеры; URL настраиваются (можно self-host) |
| STUN | ✅ | 9 публичных STUN по умолчанию; свои — через `rtcConfig` |
| **TURN** | ❌ | Встроенного нет; при symmetric NAT нужен свой coturn (бесплатно, self-hosted) |
| Browser→Go | ✅ | Go поднимает native-listener при токене; PWA уже умеет connect |
| Go как **медиа**-пир | ❌ | В Pion нет AddTrack/OnTrack; чтобы Go-пир принимал видео, нужна доработка (+1–2 нед) |
| Пропускная способность data channel | ⚠️ | flow-window 256 КиБ → goodput ≈ окно/RTT: на RTT 300 мс это ≈ 7 Мбит/с |

**Вывод.** `go-p2p-netcat` идеально закрывает **токен + discovery +
аутентификацию + надёжный control-канал** (SDP/ICE, субтитры, управление).
Медиа нужно либо вести отдельным нативным WebRTC-соединением (M1), либо
кодировать и везти по data channel (M2) — но у M2 потолок по полосе и
сложный realtime-стек.

**Ограничения, которые нужно принять в любом «браузерном» варианте:**
вкладка должна быть открыта (RTCPeerConnection доступен только в Window),
мобильный фон убивает соединение, identity сейчас эфемерная (в web/app
`createLibp2p` без ключа) → для токенов её надо персистить в IndexedDB.

**Внешние бесплатные зависимости, которые неизбежно есть:** публичные
signaling-релеи и STUN. Они не платные, но сторонние. Во всех вариантах
предусматриваем замену на свои (URL-конфиг, self-hosted relay, coturn).

## 3. Общее ядро (одинаково для всех вариантов)

- **UI-сценарий:** 4 экрана, i18n (ru/en на старте), дизайн-система, настройки
  субтитров, экран диагностики.
- **`session-core`:** state machine звонка, модель субтитров, настройки,
  события, capability-манифест языков.
- **`protocol`:** framed-протокол поверх control-канала (`HELLO`, `SDP_OFFER/
  ANSWER`, `ICE_CANDIDATE`, `SUBTITLE`, `CONTROL`, `BYE`), CBOR,
  версионирование и правила совместимости.
- **`transport-p2p`:** identity в IndexedDB, создание чата/токена, join по
  токену, listener/connect, reconnect, мост событий в UI.
- **Движки-интерфейсы:** `AsrEngine` (streaming partial/final), `MtEngine`,
  `TtsEngine` — адаптеры под каждый бэкенд. Именно поэтому A/B/C/C′ отличаются
  реализацией движков, а не всем UI.
- **Приватность/диагностика:** локальные метрики ASR/MT/сети, логи без
  содержимого речи, никакой телеметрии.

**Важное уточнение по архитектуре субтитров (по итогам исследования):**
каждый участник распознаёт **свой собственный микрофон** (свой язык известен
заранее → можно взять быстрый streaming-ASR именно для этого языка), переводит
на язык собеседника и отправляет кадр `SUBTITLE` по control-каналу. Это лучше,
чем распознавать входящее аудио: не нужен мультиязычный ASR, не тратится
трафик на передачу аудио дважды, лучше качество (чистый микрофон) и приватность.

## 4. Бесплатный стек распознавания и перевода (проверено)

### 4.1. ASR (речь → текст)

| Движок | Языки | Стриминг | Размер | Лицензия |
|---|---|---|---|---|
| **sherpa-onnx** (next-gen Kaldi) | стриминг: en, zh, ko, fr, de, es, ru (T-one, 2025-09) | **настоящий streaming + endpointing** | ~70 МБ на модель (int8) | Apache-2.0 |
| **Vosk** | ~25 языков | **настоящий streaming (partial)** | 31–50 МБ small / 0.3–2.3 ГБ big | Apache-2.0 (часть моделей NC/AGPL — проверять) |
| **whisper.cpp** | 99 | нет (VAD + окна 1–5 с) → задержка 2–5 с | tiny 75 МБ … large-v3 2.9 ГБ | MIT |
| faster-whisper (CTranslate2) | 99 | нет (VAD + чанки) | int8 ≈ ½ | MIT |
| Silero VAD | — | VAD | 0.86 МБ | MIT |
| Web Speech API | по вендору | да | 0 | не OSS; Chrome отправляет аудио в Google → не используем по умолчанию |

**Вывод:** для «на лету» нужен streaming-ASR — **sherpa-onnx** или **Vosk**.
Whisper — только как «точный» режим с задержкой 2–5 с (или на своём сервере).

### 4.2. MT (перевод)

| Решение | Языки | Размер | Качество | Лицензия |
|---|---|---|---|---|
| **Bergamot** (browsermt) | tiny ~86 пар X↔en; base 11 пар | 17–43 МБ на направление | ru→en BLEU 30.4, en→ru 28.5/COMET 0.848 | MPL-2.0 |
| **M2M100-418M** | 100 | 1.94 ГБ → ≈0.5 ГБ int8 | приемлемо | **MIT** |
| NLLB-200 distilled 600M | 202 | 2.46 ГБ → ≈0.6 ГБ int8 | лучше по редким языкам | **CC-BY-NC-4.0 (некоммерческая!)** |
| Argos Translate | 50 (через en-pivot) | 70–196 МБ/направление | средне | код MIT, модели CC-BY-4.0 |
| opus-mt | 1000+ пар | ≈80 МБ int8 | слабее | CC-BY-4.0 |
| Локальная LLM (Qwen3-4B и т.п.) | 100+ | 2.5–3.5 ГБ | лучше по контексту | Apache-2.0 |

**Вывод:** для браузера — **Bergamot WASM** (быстро, маленький) для
поддерживаемых пар; для сервера/десктопа — **M2M100 (MIT)** как
«безопасный по лицензии» дефолт, **NLLB-600M** — только если проект
некоммерческий. Это важное ограничение: NLLB нельзя использовать в
коммерческом продукте.

### 4.3. TTS (опция, не в MVP)

- Голоса ОС: Web Speech Synthesis (браузер), AVSpeech/System.Speech,
  Android TTS — бесплатно, без лицензионных мин.
- Piper — GPL-3.0 (с 2025 г. `piper1-gpl`), Coqui XTTS — CPML
  (некоммерческая). В MVP не берём; опция «озвучивать перевод» — через
  системный TTS.

### 4.4. Commit-стратегия для «живых» субтитров

VAD (Silero) → streaming-ASR → **LocalAgreement-2** (фиксируем префикс,
совпавший в двух последних гипотезах) → MT только по зафиксированным
предложениям (не чаще ~1 раза в 300–500 мс) → UI (серый «черновик» /
финальный текст). Это даёт 0.7–1.8 с задержки и убирает «мигание» перевода.
Дополнительно: пунктуация/капитализация моделью (sherpa-onnx punctuation),
фильтр галлюцинаций Whisper (`no_speech_threshold`,
`condition_on_previous_text=false`).

## 5. Вариант A — «Всё в браузере» (PWA: M2 + WASM-модели)

**Идея:** одно статическое веб-приложение, ноль установок и серверов.
Медиа кодируется WebCodecs и едет по data channel `go-p2p-netcat`; перевод —
WASM-модели (sherpa-onnx + Bergamot) прямо в браузере.

**Поток данных:**

```
getUserMedia ─► WebCodecs VideoEncoder/AudioEncoder ─► пакетизатор
   ─► RTCDataChannel (native WebRTC listener из p2p-netcat-core)
   ─► jitter buffer ─► декодер ─► <video>/<canvas> + WebAudio

свой микрофон ─► VAD ─► sherpa-onnx WASM ─► Bergamot WASM ─► SUBTITLE кадры
                                                                  │
приёмник: SUBTITLE ─► sherpa-onnx WASM VITS (голос ru/en) ─► WebAudio:
          озвучка 100 % + оригинал 20–30 % (ducking)
```

**Ключевые ограничения (проверено):**
- data channel — **ordered + reliable**, flow-window 256 КиБ → на RTT 300 мс
  потолок ≈ 7 Мбит/с; при 3–5 % потерь head-of-line blocking даёт 0.5–2 с
  задержки. Для 480p это ещё ок, для 720p — на грани.
- WebCodecs: Chrome/Edge 94+, Firefox desktop 130+, **Firefox Android — нет**,
  Safari — частично до 26+. То есть мобильный браузер часто отпадает.
- Нужно написать с нуля: пакетизатор, jitter buffer, A/V sync, оценку полосы
  (AIMD/GCC), запрос keyframe, обработку потерь. Это 1500–2500 строк
  рискованного realtime-кода.
- **Дубляж:** TTS (`sherpa-onnx WASM VITS` + piper-голоса ru/en) синтезирует
  перевод на приёмнике; WebAudio-граф приглушает оригинал и микширует;
  fallback — Web Speech Synthesis. Задержка TTS 0.1–0.6 с.

**Плюсы:** ничего не устанавливается; ссылка с токеном → звонок; речь не
покидает устройство; максимум «чистого P2P».

**Минусы:** самый сложный realtime-код; потолок полосы; WASM-ASR на телефоне
не успевает; Bergamot — ограниченный набор пар; Safari/Firefox Android;
велик риск, что «на реальных устройствах еле живёт».

**Оценка:** ~80–90 мелких коммитов, из них половина — рискованный realtime
(медиа + TTS). Time-to-demo — дольше, чем у B.

**Кому:** если критично «ничего не устанавливать и никаких серверов», и
допустимо качество «демо/пилот» на ограниченном наборе языков.

**Вердикт:** **выбран заказчиком (2026-11-07)**. Требует дисциплины: спайки
P3A-01/P5A-01/P5T-01 до основного кода и запасной путь через нативное медиа
(D16), если data-channel-медиа не потянет. Дубляж полностью локален и не
требует серверов.

## 6. Вариант B — «Тонкий клиент + свой переводчик» ⭐ рекомендуется

**Идея:** PWA с **нативным WebRTC** для медиа (M1). `go-p2p-netcat` —
identity, токен, discovery, аутентификация и **control-канал** (SDP/ICE,
субтитры, управление). Перевод — подключаемый бэкенд: сначала
**WASM-фолбэк** (sherpa-onnx + Bergamot), для качества — **свой
self-hosted `lingua-node`** (Whisper/M2M100, бесплатно, на ноутбуке/LAN/VPS).

**Архитектура (подвариант B2 — два WebRTC-соединения):**

```
Браузер A                                             Браузер B
┌───────────────────────────────┐      ┌───────────────────────────────┐
│ UI (React)                    │      │ UI (React)                    │
│ identity в IndexedDB          │      │ identity в IndexedDB          │
│ transport-p2p:                │      │ transport-p2p:                │
│   listener / connect по токену│◄────►│   connect по токену           │
│   WebRtcStream (data channel) │ p2p  │   WebRtcStream (data channel) │
│   = CONTROL: HELLO, SDP, ICE, │      │                               │
│     SUBTITLE, CONTROL, BYE    │      │                               │
│ media-rtc: RTCPeerConnection  │◄════►│ media-rtc: RTCPeerConnection  │
│   addTrack(audio,video)       │ UDP  │   (медиа напрямую)            │
│ ASR+MT: WASM или lingua-node  │      │ ASR+MT                        │
└──────────────┬────────────────┘      └───────────────────────────────┘
               │ WebSocket (локальный/свой сервер)
               ▼
        lingua-node (self-hosted, бесплатно)
        streaming sherpa-onnx / whisper.cpp + M2M100 + (опц. TTS ОС)
```

**Как устроено (проверено по коду):**
- **Control-канал:** браузер-слушатель через `startNativeWebRtcListener`,
  клиент — `connectNativeWebRtc`; токен — `createPairingToken`; для listener
  нужна персистентная Ed25519-identity (IndexedDB) и `createAuthResponse =
  signWebRtcAuthResponseV2`; серверная часть токена — `authenticateServerStream`.
  Поверх потока — наш framed-протокол (`HELLO`, `SDP`, `ICE`, `SUBTITLE`, …).
  **Go-часть не меняется** — она просто носит байты.
- **Медиа:** **второй** `RTCPeerConnection` с `addTrack()`; SDP/ICE — JSON-кадрами
  по control-каналу (помечаем `media:1` в `HELLO`). Изоляция: падение
  медиа-ICE не рвёт чат/субтитры. Браузер сам делает congestion control,
  NACK/FEC, jitter buffer, echo cancellation, Opus FEC.
- **Связывание двух соединений:** app-level проверка, что оба peer'а — те же
  (хэш SHA-256 SDP в control-канале), т.к. DTLS у двух PC разный.
- **Субтитры:** каждый распознаёт свой микрофон (sherpa-onnx/Vosk streaming),
  переводит на язык собеседника (Bergamot WASM / M2M100) и отправляет
  `SUBTITLE` по control-каналу; приёмник отображает. Собеседник может видеть
  оригинал + перевод.
- **`lingua-node`** (опция качества): WebSocket API `{audioChunk, srcLang,
  dstLang}` → `{partial, final, text}`; внутри — streaming sherpa-onnx или
  whisper.cpp large-v3-turbo (на GPU/Apple Silicon) + M2M100 int8; запуск —
  `docker compose up` или один бинарь; health-check в UI.
- **NAT:** публичный STUN по умолчанию; при symmetric NAT — **свой coturn**
  (бесплатно) или fallback A (видео по control-каналу через relay/WSS).

**Плюсы:**
- Лучший баланс: нативное медиа (качество, адаптация, эхо) + нормальные
  ASR/MT-модели.
- Один UI/протокол для web и desktop; ссылка с токеном работает на телефоне.
- Без платных сервисов; узел — свой или вообще `localhost`.
- Постепенная деградация: без узла — WASM; с узлом — качество.
- Меньше рискованного realtime-кода; Go не трогаем.

**Минусы:**
- Для хорошего качества нужен свой `lingua-node` (Docker/бинарь) — доп. шаг
  для пользователя; в первой версии узел опционален (WASM-фолбэк).
- Вкладка должна быть открыта; мобильный фон убивает звонок (лечится оболочкой
  Tauri/Capacitor позже).
- Речь уходит на узел, если он не на `localhost` — приватность честно объяснять.
- Нужен coturn для части NAT; встроенного TURN нет.
- Совместимость с Go-пиром по медиа отсутствует (Go не умеет addTrack);
  медиа — только между «нашими» клиентами. Чат/субтитры с Go-пиром — да.

**Оценка:** ~60–75 мелких коммитов. По фазам (по исследованию):
Фаза 1 (identity в IndexedDB + токен в UI + listener + `authenticateServerStream`
+ второй PC с медиа + signaling поверх потока + UI звонка) — 8–10 коммитов;
Фаза 2 (капабилити `media:1`, чат/субтитры в том же потоке, reconnect) — 5–7;
Фаза 3 (WASM ASR/MT, настройки субтитров) — 8–10; Фаза 4 (lingua-node,
coturn, фолбэк A) — 8–10. Time-to-demo — самый короткий.

**Вердикт:** рекомендую как основной.

## 7. Вариант C — «Десктоп, всё локально» (Tauri + sidecars + локальные модели)

**Идея:** нативное десктоп-приложение (Tauri 2, тот же React UI). Sidecar
`p2p-nc` (Go) как транспорт; локальные модели: streaming sherpa-onnx/Vosk +
whisper.cpp (Metal/CUDA) как точный режим + M2M100/Bergamot. **Полный офлайн**
после первой загрузки моделей, никаких серверов.

**Архитектура:**

```
Tauri app
├─ React UI (apps/web)
├─ Rust core: IPC/события, управление sidecar'ами, разрешения mic/cam
├─ sidecar p2p-nc (Go): listener/connect по токену, control-поток
├─ ASR sidecar: sherpa-onnx streaming (+ whisper.cpp для точного режима)
├─ MT sidecar: M2M100 int8 / Bergamot; опц. TTS голосом ОС
└─ media: RTCPeerConnection в webview + SDP/ICE по control-потоку p2p-nc

A(desktop) ◄══ WebRTC media ══► B(desktop)
             control — через p2p-nc (SDP/ICE/субтитры)
```

- Токен и listener — `p2p-nc` (Go): стабильный PeerId, приватный rendezvous,
  DHT/QUIC/relay; браузерный клиент тоже сможет подключиться (совместимо).
- Медиа — webview (WKWebView/WebView2); при проблемах — позже нативный
  webrtc-rs, но начинать проще с webview.
- Модели скачиваются при первом запуске (0.5–1.5 ГБ), проверяются по checksum,
  кэшируются; int8/q5 для экономии.
- UI — тот же, что в B; отличие только в реализации движков и оболочке.

**Плюсы:** лучшее качество и задержка (streaming ASR + M2M100 на своём
железе, Metal на M1); полный офлайн; максимальная приватность; p2p-nc
используется по максимуму; та же кодовая база → миграция из B дешёвая.

**Минусы:** только десктоп; размер дистрибутива; упаковка/подпись/обновления/
разрешения камеры в webview; больше платформенного кода; кросс-ОС WebRTC
в webview нужно тестировать.

**Оценка:** ~75–90 мелких коммитов; много платформенной/упаковочной работы.
Time-to-demo — позже B, качество — выше.

**Кому:** если приоритет — качество/офлайн/приватность и звонки между
компьютерами; установка приложения допустима.

**Вердикт:** лучший «премиум»-вариант; естественный этап 2 после B (тот же
UI, добавляется оболочка и локальные движки).

## 8. Вариант D — «Android-приложение» (Kotlin/Compose + локальные модели)

**Идея:** нативное мобильное приложение — «как Zoom/WhatsApp, но P2P и с
живым переводом».

**Архитектура:**
- UI: Kotlin + Jetpack Compose; 4 экрана.
- Транспорт: **нужен мост к `go-p2p-netcat`**. Варианты: (а) gomobile-биндинг
  Go-библиотеки (такого API сейчас нет — доработка в go-p2p-netcat),
  (б) WebView с PWA (variant B внутри), (в) Kotlin-реализация протокола
  (очень много). Рекомендуемый — (а), но это отдельный подготовительный
  проект.
- Медиа: `org.webrtc:google-webrtc` + signaling по control-каналу.
- ASR: `sherpa-onnx`/Vosk-Android (стриминг) — реально на телефоне.
- MT: M2M100 int8 через ONNX Runtime Mobile (200–600 МБ) — тяжело; на слабых
  устройствах — перевод на своём узле (B-сервер).
- TTS: Android TextToSpeech (офлайн-голоса ОС).

**Плюсы:** настоящий мобильный опыт, push-уведомления, батарея; локальные
ASR-модели реальны; максимальный охват.

**Минусы:** самый большой объём работ (сначала gomobile-биндинг транспорта,
потом приложение, потом модели под ARM); тяжёлые MT-модели на телефоне;
Google Play; iOS — отдельный мир; сейчас p2p-netcat Android — shell-бинарник
через adb, а не библиотека.

**Оценка:** ~100+ мелких коммитов + работа в репозитории go-p2p-netcat. Самый
долгий путь к демо.

**Вердикт:** не первый вариант; логичное продолжение B/C после MVP.

## 10. Рекомендация

**Рекомендация была B**, но заказчик выбрал **A** (полностью в браузере) и
подтвердил, что дубляж — главная фича. План перестроен под A: TTS локально у
приёмника, D16 оставляет путь к нативному медиа, если data channel не потянет.
Ниже — исходное обоснование B (история решения).

Почему:

1. **Быстрее всех до работающего продукта.** Медиа делает браузер (нативный
   WebRTC), сложный realtime-стек не пишем. `go-p2p-netcat` используется по
   назначению: токен, discovery, аутентификация, control-канал (SDP/ICE,
   субтитры, управление). Go-часть не меняется.
2. **Достижимое качество перевода.** `lingua-node` на своём железе даёт
   streaming-ASR + M2M100 (MIT) на десятки языков; WASM-фолбэк позволяет
   работать вообще без инфраструктуры.
3. **Максимальный охват:** ссылка с токеном открывается на компьютере и
   телефоне, ничего не устанавливая.
4. **Нет платных сервисов:** узел — свой (localhost/LAN/VPS), модели —
   open-source (обязательно MIT/Apache/MPL/CC-BY, не NC); signaling/STUN можно
   self-host.
5. **Плавная эволюция в C и D:** UI, протокол, модель субтитров и интерфейсы
   движков переиспользуются; desktop-оболочка Tauri добавляется поверх,
   Android — через WebView/gomobile позже.

**Если приоритет иной:**
- «Полный офлайн и без серверов вообще» → **вариант C**.
- «Только браузер и никаких серверов» (готовы к ограничениям) → **вариант A**.
- «Нужно именно мобильное приложение» → **вариант D**, с пониманием, что
  сначала придётся доработать go-p2p-netcat (gomobile).

### Дорожная карта внутри B (если выбираем его)

1. **Демо №1 (без узла):** identity в IndexedDB, генерация токена в UI,
   browser-listener, второй PC с медиа, signaling поверх control-потока,
   UI звонка; субтитры ru↔en на sherpa-onnx WASM + Bergamot WASM.
2. **Демо №2 (с узлом):** `docker compose up lingua-node` → качественные
   субтитры на 10+ языков, задержка ≤ 2 с.
3. **Надёжность:** coturn по желанию, fallback A при провале медиа-ICE,
   reconnect, диагностика.
4. **Дальше:** desktop-оболочка Tauri с локальными движками (= вариант C) без
   переписывания; Android — отдельный трек.

## 11. Лицензионные ограничения (важно!)

Требование «без платных сервисов» выполняется, но лицензии моделей накладывают
ограничения на **коммерческое** использование:

- ✅ можно: whisper.cpp (MIT), sherpa-onnx (Apache-2.0), Vosk (Apache-2.0, но
  проверять модели), M2M100 (MIT), Bergamot (MPL-2.0), Argos (MIT код,
  CC-BY-4.0 модели), Silero VAD (MIT), opus-mt (CC-BY-4.0).
- ⛔ **NLLB-200 — CC-BY-NC-4.0** (некоммерческая). Нельзя в коммерческий
  продукт без отдельной лицензии.
- ⚠️ Silero STT/TTS — CC-BY-NC; Piper — GPL-3.0 (с 2025 `piper1-gpl`);
  LibreTranslate — AGPL-3.0; часть моделей Vosk — AGPL/NC. Проверять каждую
  модель; для MVP TTS не берём (системные голоса ОС).

В `PLAN.md` это отдельное решение (D11) и обязательный пункт ревью при
добавлении любой модели.
